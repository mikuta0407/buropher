# buropher DB schema

This document describes the database schema of buropher (initial migration `00001_initial_schema`)
and records where it deviates from Redmine 6.1.2. The design basis is the internal planning
document "Appendix A: Redmine DB schema analysis"; decisions taken while implementing it
(gaps, contradictions) are listed in [Decisions and deviations](#decisions-and-deviations).

## Files and workflow

| Path | Purpose |
|---|---|
| `internal/db/migrations/src/*.sql.tmpl` | **Source of truth.** Dialect-neutral template (Go `text/template`). |
| `internal/db/migrations/sqlite/*.sql` | Generated goose migration for SQLite. Do not edit. |
| `internal/db/migrations/postgres/*.sql` | Generated goose migration for PostgreSQL. Do not edit. |
| `internal/db/internal/migrationgen` | Generator (`go generate ./internal/db`). |

* Both dialects always have the same migration versions/file names (enforced by a test).
* `TestGeneratedMigrationsUpToDate` fails if the generated files are stale.
* The `-- +goose Down` section is generated automatically (DROP TABLE in reverse creation order).
* Later migrations may be written as templates as well (recommended) or by hand in both directories
  with the same version number.
* Migration history is stored in the `schema_migrations` table (goose format, not Redmine's).

### Template helpers → type mapping

| Template | Logical type | SQLite | PostgreSQL |
|---|---|---|---|
| `{{pk}}` | surrogate key `id` | `INTEGER PRIMARY KEY AUTOINCREMENT` | `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` |
| `{{ref}}` | FK / 64-bit integer | `INTEGER` | `BIGINT` |
| `TEXT` | string | `TEXT` | `TEXT` |
| `{{bool "c" d}}` | boolean | `INTEGER NOT NULL DEFAULT d CHECK (c IN (0,1))` | `BOOLEAN NOT NULL DEFAULT d` |
| `{{ts "c"}}` | UTC timestamp | `TEXT CHECK (c GLOB 'YYYY-MM-DDTHH:MM:SS.ffffffZ')` | `TIMESTAMPTZ` |
| `{{date "c"}}` | calendar date | `TEXT CHECK (c GLOB 'YYYY-MM-DD')` | `DATE` |
| `{{json "c"}}` | JSON | `TEXT CHECK (json_valid(c))` | `JSONB` |
| `{{real}}` | float | `REAL` | `DOUBLE PRECISION` |
| `{{latefk ...}}` | forward-reference FK | inline `REFERENCES` | `ALTER TABLE ... ADD CONSTRAINT` at the end |

All booleans and timestamps are `NOT NULL` unless the column is semantically optional.
Enumerations are `TEXT`/`INTEGER` + `CHECK (... IN (...))` (no PG ENUM types).

## Conventions

* **IDs are preserved** from Redmine on import (URLs, REST API, `#123` links). After an import with
  explicit ids call `Dialect.ResetSequence(table)` (PG `setval`; SQLite `sqlite_sequence` is
  maintained automatically but is also corrected).
* **Timestamps are UTC**, column names `*_at` (Redmine `*_on` renamed). SQLite stores the fixed-width
  text `2006-01-02T15:04:05.000000Z` (always 6 fractional digits, so text order = time order), enforced
  by a `GLOB` CHECK. Go code reads/writes them via `db.Time` / `db.NullTime` (and `db.Date` /
  `db.NullDate` for dates). PG sessions run with `timezone=UTC`.
* **Foreign keys everywhere.** Owned rows: `ON DELETE CASCADE`. Optional references:
  `ON DELETE SET NULL`. Master data (tracker, status, priority, activity, role, document category) and
  authorship (`author_id`, `user_id` of journals / time entries ...): `RESTRICT` — the application
  reassigns to the anonymous user before deleting a user, exactly like Redmine; the FK catches omissions.
* **Self references are `DEFERRABLE INITIALLY DEFERRED`** (projects.parent_id, issues.parent_id/root_id,
  member_roles.inherited_from, wiki_pages.parent_id, boards.parent_id, messages.parent_id/last_reply_id,
  time_entry_activities.parent_id, boards.last_message_id). Where Redmine "restricts" such a delete we
  use the default `NO ACTION` (PG cannot defer `RESTRICT`).
* **Polymorphic associations** that survive (`attachments`, `custom_values`, `watchers`, `reactions`)
  use `*_kind` + `*_id` with a CHECK on the kind and a composite index. They have no FK; the
  application deletes them when the owner is deleted, and `buropher db check` (planned) detects orphans.
* **Case-insensitive uniqueness** uses `lower(col)` expression indexes (login, e-mail address,
  wiki page title).
* **No triggers.** Derived values (counters, `tyear/tmonth/tweek`, `hier_path`, closure rows,
  `position_name`) are maintained in Go.
* SQL in Go is written with `?` placeholders; `db.DB`/`db.Tx` rebind them for PG (`$n`). Hence the
  PG jsonb `?` operators must not be used (use `jsonb_exists()`), and `?` must not appear in string
  literals of queries.

## Decisions and deviations

Decisions taken where the planning documents were silent or contradictory:

1. **`auth_sources` is generalised** (auth design doc: `kind` ldap/oidc + `config` JSON) instead of
   the appendix's `ldap_auth_sources` with typed columns. LDAP settings live in `config`; the bind
   password is the separate `secret` column so it can be encrypted independently. `name` is unique
   (Redmine validates it).
2. **Notification settings are normalised** into `user_notification_settings` (from the
   notifications design doc). Consequently `mail_notification` is *not* on `user_accounts`, and
   `no_self_notified` / `notify_about_high_priority_issues` are *not* on `user_preferences`, although
   the appendix lists them there. `members.mail_notification` became `user_notified_projects`.
3. **`tokens` keeps its name** (the auth doc mentioned `auth_tokens` once) but loses the `session`
   action (→ `sessions`) and `twofa_backup_code` (→ `twofa_backup_codes`, stored hashed since codes
   are shown only once).
4. **`hier_path` includes the issue itself** as the last element
   (`0000000012/0000000045/` for issue 45 under root 12). `ORDER BY root_id, hier_path` reproduces
   Redmine's `lft` order; descendants are `hier_path LIKE '<path>%' AND id <> <self>`.
   A new root issue is inserted with a placeholder `root_id` (e.g. 0) / `hier_path` and fixed by an
   `UPDATE` in the same transaction — the deferred self-FK makes this legal.
5. **`project_closure` contains self rows** (depth 0) to simplify "project and its subprojects" queries.
6. **`principals.name`** holds group names (appendix §5.3); users keep `firstname`/`lastname`.
7. **`queries`:** only `totalable_names` and `display_type` are promoted to columns; the other
   option keys (`draw_relations`, `draw_progress_line`, `draw_selected_columns`, ...) stay in the
   `options` JSON.
8. **`custom_values (custom_field_id, value)` index was not created**: PG B-tree entries are limited
   to ~2.7 kB and long text values would make inserts fail. Revisit with an expression index on a
   prefix if filtering becomes slow.
9. **NOT NULL tightened** for columns that Redmine leaves nullable but always fills in practice
   (`*.created_at`, `members.created_at`, `time_entries.author_id`, positions, `versions.name/status`,
   `roles.name`, `messages.locked/sticky`, `news.project_id`, `boards.description`, ...). The importer
   fills defaults as specified in Appendix A §4.7.
10. **`''` → NULL** for optional text (`homepage`, `language`, `time_zone`, `notes`, `description`,
    `regexp`, `default_value`, `custom_values.value`, ...). `issue_journal_details` values are kept
    verbatim.
11. **Uniqueness enforced in the DB** that Redmine only validates in the application: status /
    tracker / role / priority / document category names, (owner_kind, name) for custom fields,
    (project_id, name) for versions and categories, activity names per project, one wiki per project,
    (wiki_id, lower(title)) for pages, one default e-mail per user. The importer must report and
    resolve duplicates.
12. **Polymorphic kinds are snake_case**, `EnabledModule` → `project_module`, `Principal` → `principal`,
    `Enumeration` → `enumeration`.
13. **SQLite tables are not `STRICT`**, to keep driver interop simple; the type discipline is
    enforced by the CHECK constraints on booleans, timestamps, dates and JSON instead.
14. **`wiki_page_versions.author_id` / `messages.author_id`** stay nullable (as in Redmine) but use
    `RESTRICT` like other authorship columns.
15. **SQLite connections** use `_txlock=immediate` (`BEGIN IMMEDIATE`) to avoid lock-upgrade
    deadlocks under concurrent writers; read-only work should not be wrapped in `WithTx`
    unnecessarily.
16. **`Tx.DeferConstraints`** defers *all* FKs on SQLite (`PRAGMA defer_foreign_keys`) but only the
    `DEFERRABLE` ones on PG (`SET CONSTRAINTS ALL DEFERRED`). The importer should therefore insert in
    dependency order (Appendix A §6.1) and rely on deferral only for self references and the
    `projects.default_*` / `boards.last_message_id` cycles (the latter are filled by a later UPDATE).

## Redmine columns intentionally not carried over

| Redmine | Reason |
|---|---|
| `projects.lft/rgt`, `issues.lft/rgt` | Replaced by closure table / `hier_path`. |
| `users.type`, `users.salt`, `users.hashed_password` | → `principals.kind`, `user_accounts.password_hash`. |
| `enumerations.type`, `custom_fields.type`, `queries.type`, `repositories.type`, `imports.type`, `workflows.type` | Split tables or `kind` columns. |
| `workflows.new_status_id` for permissions, `workflows.field_name` numeric | → `workflow_field_rules.custom_field_id`. |
| `wikis.status` | Always 1, unused. |
| `wiki_content_versions.compression`, `wiki_contents` | Versions stored uncompressed in one table. |
| `journals.journalized_type`, `comments.commented_type` | Only Issue / News exist in core. |
| `schema_migrations`, `ar_internal_metadata` | Rails internals; buropher uses goose's own `schema_migrations`. |
