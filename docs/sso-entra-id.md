# シングルサインオン（OIDC / Microsoft Entra ID）の設定

buropher は Redmine には無い拡張として、OpenID Connect（OIDC）によるシングルサインオンに対応している。
Microsoft Entra ID（旧 Azure AD）用のプリセットがあり、Keycloak・Google Workspace・Okta などの汎用 OIDC
プロバイダも「汎用 OpenID Connect」で使える。

実装: `internal/auth/oidc`（プロトコル）、`internal/handler/oidc_login.go`（ログイン・ユーザー解決・グループ同期）、
`internal/handler/auth_sources_oidc.go`（管理画面）、`internal/handler/my_identities.go`（マイアカウントの連携一覧）。

## 1. 仕組み

- 認可コードフロー + PKCE（S256）。`state`（CSRF 対策、10 分で失効）と `nonce`（ID トークンの再利用防止）を
  セッションに保存して callback で照合する。ID トークンの署名はプロバイダの JWKS で検証する（ディスカバリ結果と
  JWKS は 1 時間キャッシュ）。
- エンドポイント: `GET /auth/oidc/<id>/start`（IdP へリダイレクト）、`GET /auth/oidc/<id>/callback`（リダイレクト URI）。
- ユーザーの解決順:
  1. `user_identities`（provider = `oidc:<認証方式 id>`、subject = サブジェクトのクレーム）に連携があればそのユーザー
  2. 「既存ユーザーとの突合」（メールアドレス / ログイン ID）で一致したユーザーに連携を作る（**初回だけ**。以後は 1 で固定。
     既に同じ認証方式の別の ID と連携しているユーザーには紐付けない）
  3. 「オンザフライ登録」が有効ならユーザーを作成する（認証方式 = この OIDC。パスワードではログインできない）
  4. いずれでもなければログインを拒否する
- グループ同期: 「グループを同期する」が有効なら、ログインのたびに `groups` クレームと対応表に従って buropher の
  グループの所属を追加・削除する。**対応表に現れるグループだけ**を操作し、それ以外の所属には触れない。
  グループ経由でプロジェクトのロールが付くため、プロジェクトの権限を IdP のグループで管理できる。
- アカウントの状態: ロック・未有効化のユーザーは SSO でもログインできない（Redmine と同じメッセージ）。

## 2. Microsoft Entra ID 側の設定

1. [Microsoft Entra 管理センター](https://entra.microsoft.com/) → **アプリの登録** → **新規登録**
   - 名前: 任意（例: `buropher`）
   - サポートされているアカウントの種類: 通常は「この組織ディレクトリのみ（シングルテナント）」
   - リダイレクト URI: プラットフォーム **Web**、`https://<buropher のホスト>/auth/oidc/<id>/callback`
     （`<id>` は buropher で認証方式を作成した後に編集画面の「リダイレクト URI」に表示される。先に buropher 側で
     作成してから登録するか、作成後にアプリの「認証」で追加する）
2. **概要** の「アプリケーション (クライアント) ID」と「ディレクトリ (テナント) ID」を控える。
3. **証明書とシークレット** → **新しいクライアント シークレット** を作成し、値を控える（有効期限に注意）。
4. **API のアクセス許可**: 既定の `Microsoft Graph / User.Read`（委任）のままでよい。`openid` `profile` `email` は
   OIDC のスコープとして要求する（管理者の同意が必要な組織では「管理者の同意を与えます」）。
5. **トークン構成**（任意）:
   - グループ同期・グループ制限を使う場合は **グループ要求を追加** → 「セキュリティ グループ」（または
     「アプリケーションに割り当てられたグループ」）を選び、ID トークンにグループの **オブジェクト ID** を含める。
   - メールアドレスが空のユーザーがいる場合は省略可能な要求 `email` を追加する（無い場合は `preferred_username`
     （UPN）をメールアドレスとして使う）。
6. （任意）**エンタープライズ アプリケーション** → 該当アプリ → **プロパティ** で「割り当てが必要」を有効にすると、
   割り当てたユーザー・グループだけがサインインできる。
7. （任意）ログアウト連携: アプリの **認証** → 「フロントチャネルのログアウト URL」は不要。RP-Initiated Logout の
   戻り先として `https://<buropher のホスト>/` をリダイレクト URI に追加しておく（`post_logout_redirect_uri`）。

## 3. buropher 側の設定

管理 → **LDAP 認証**（認証方式の一覧）→ **新しい OpenID Connect プロバイダ**（`/auth_sources/new?type=AuthSourceOidc`）。

| 項目 | Entra ID での値 | 説明 |
|---|---|---|
| 名前 | 例: `Microsoft` | ログイン画面のボタン「Microsoft でログイン」に使う |
| 有効 | ✓ | 無効にするとボタンが消え、callback も 404 |
| プリセット | Microsoft Entra ID | issuer・サブジェクト（`oid`）・テナント（`tid`）の既定値が Entra 用になる |
| Issuer URL | 空欄 | 空欄ならテナントから `https://login.microsoftonline.com/<テナント>/v2.0` を組み立てる |
| テナント | ディレクトリ (テナント) ID | ドメイン名（`contoso.onmicrosoft.com`）も可。マルチテナントは `organizations` / `common` |
| クライアント ID | アプリケーション (クライアント) ID | |
| クライアントシークレット | 手順 2-3 の値 | `server.secret_key` から導いた鍵で暗号化して保存する（`sb1:`） |
| スコープ | `openid profile email` | |
| ボタンの表示名 | 任意 | 空欄なら「<名前> でログイン」 |
| オンザフライ登録 | 任意 | 未登録のユーザーを自動作成する |
| 既存ユーザーとの突合 | メールアドレス（既定） | Redmine から移行したユーザーを初回ログイン時に紐付ける |
| クレームの対応 | 空欄（既定値） | Entra: subject=`oid`、login=`preferred_username`、名=`given_name`、姓=`family_name`、mail=`email`、groups=`groups`、tenant=`tid` |
| 許可するテナント | テナント ID | マルチテナント構成では**必ず**指定する |
| 許可するグループ | 任意 | グループのオブジェクト ID を 1 行に 1 つ。いずれかに所属するユーザーだけログイン可 |
| シングルサインオンを必須にする | 任意 | 下記 4 |
| プロバイダの多要素認証を信頼する | ✓（既定） | 有効なら SSO ログインで buropher の 2 要素認証を求めない（2FA 必須設定でも有効化を求めない） |
| プロバイダからもログアウトする | 任意 | ログアウト後に Entra の `end_session_endpoint` へリダイレクトする（`id_token_hint`・`post_logout_redirect_uri` 付き） |
| グループを同期する・対応表 | 任意 | 「プロバイダのグループ」にグループのオブジェクト ID、右に buropher のグループ |

保存後、一覧の **テスト** でディスカバリ（`/.well-known/openid-configuration`）を確認できる。
編集画面に表示される **リダイレクト URI** を Entra のアプリに登録する。

`server.base_url`（環境変数 `BUROPHER_BASE_URL`）を設定している場合、リダイレクト URI はそれを基準に作る。
リバースプロキシの背後では `base_url` を設定すること（未設定ならリクエストのスキームとホストを使う）。

## 4. SSO 必須モード

いずれかの有効な OIDC 認証方式で「シングルサインオンを必須にする」を有効にすると:

- ログイン画面はパスワードのフォームを隠し、SSO のボタンと「ローカルアカウントでログイン（管理者）」のリンク
  （`/login?local=1`）だけを表示する。
- 管理者以外のパスワードログインは拒否する（「パスワードでのログインは無効です」）。管理者は救済用に
  `/login?local=1` からパスワードでログインできる。
- REST API は API キー（`X-Redmine-API-Key`・`key` パラメータ・ユーザー名欄に API キーを入れる Basic 認証）なら
  従来どおり使える。ログイン名とパスワードによる Basic 認証は管理者以外拒否する（IdP 側で無効化したり
  MFA を強制したりしたユーザーが、ローカルのパスワードで API を使い続けられないようにするため）。

## 5. マイアカウントの連携

OIDC 認証方式があると、マイアカウントのサイドバーに「連携アカウント」（`/my/sso`）が出る。

- 連携中の外部 ID の一覧（プロバイダ・メールアドレス・作成日時・最終ログイン）と **連携解除**。
  パスワードでログインできないユーザー（SSO で作成されたユーザー）の最後の連携は解除できない。
- 未連携の認証方式の **<名前> と連携** で、ログイン中のアカウントに外部 ID を紐付ける（メールアドレスが一致しなくてよい。
  他のアカウントに連携済みの ID は紐付けない）。

## 6. 2 要素認証・sudo モードとの関係

- 「プロバイダの多要素認証を信頼する」が無効で、ユーザーが buropher の 2 要素認証を有効にしている場合は、SSO の後に
  TOTP の入力（`/account/twofa/confirm`）を求める。
- sudo モード（`[auth] sudo_mode = true`）のパスワード再入力フォームには、外部 ID と連携しているユーザーに
  「<名前> で確認」ボタンを出す。IdP で再認証（`prompt=login`）すると sudo が有効になり、元の画面
  （GET なら同じ URL、POST なら Referer）へ戻る。POST の送信内容は引き継がないため、もう一度操作する。

## 7. 制限・注意

- Entra のグループ超過（ユーザーのグループが 200 を超え、ID トークンに `_claim_names.groups` が入る場合）は
  Microsoft Graph による取得に対応していない。その場合はグループ同期を行わず、ログに警告を出す
  （「アプリケーションに割り当てられたグループ」に絞ると超過を避けられる）。許可するグループの判定ではグループ無しとして扱う。
- マルチテナント（`organizations` / `common`）では ID トークンの `iss` が `https://login.microsoftonline.com/<tid>/v2.0`
  であることを確認し、subject は `<iss>|<oid>` として名前空間を分ける。
- ID トークンの `email` は Entra では検証済みとは限らない。「既存ユーザーとの突合」をメールアドレスにする場合は、
  テナントを自組織に限定すること（シングルテナント、または許可するテナント）。マルチテナント構成では、
  省略可能な要求 `xms_edov`（メールのドメイン所有者が検証済み）が `true` のときだけメールアドレスで突合する
  （無い・`false` なら、`email` が無く UPN を代わりに使う場合も含めて未検証として扱い、既存ユーザーに紐付けない。nOAuth 対策）。
- 「プロバイダの多要素認証を信頼する」が有効な場合、buropher の 2 要素認証を有効にしているユーザーには
  「既存ユーザーとの突合」で自動的に紐付けない（紐付けると以後 2 要素認証を迂回できるため）。そのユーザーは
  パスワード + 2 要素認証でログインし、マイアカウントの「外部 ID 連携」から連携する。
- ID トークンは署名（RS256 等の公開鍵方式のみ。`none` / HS256 は拒否）・`iss`・`aud`・`exp`・`nonce` に加え、
  `aud` が複数の場合や `azp` がある場合は `azp` がこのクライアント ID であることを確認する。
- 汎用の OIDC プロバイダでは `email_verified` が `false` のメールアドレスで既存ユーザーと突合しない。
  「ログイン ID」での突合は、利用者が IdP でそのクレーム（既定は `preferred_username`）を変更できない場合だけ使うこと
  （OpenID Connect Core は `preferred_username` が一意・不変であることを保証しない）。
- SAML には対応していない。
